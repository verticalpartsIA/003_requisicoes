# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VPRequisições — internal requisition/procurement platform for VerticalParts.
Requests flow through modules **M1-M6** (Products, Trips, Services,
Maintenance, Freight, Rental) plus **M7** (Quadro de Comando, elevator
control-panel spec form), then through stages **V2-V5** (Quotation →
Approval → Purchase → Receipt). Full product overview: `README.md`. Recent
work and links to detailed incident/feature reports: `CHANGELOG.md`.

## Commands

```bash
npm run dev         # vite dev server
npm run build       # scripts/build.mjs -> vite build (writes dist/client + dist/server)
npm run start        # node server.js — serves the build (production entry point)
npm run typecheck    # tsc --noEmit
npm run lint          # eslint .
npm run format        # prettier --write .
npm test              # vitest run (all tests)
npx vitest run path/to/file.test.ts   # single test file
npx vitest run -t "test name"          # single test by name
```

Always run `typecheck` + `lint` + `test` before considering a change done —
`eslint` here enforces `prettier` formatting as lint errors, so
`npx prettier --write <file>` after editing a previously-unformatted file
resolves most of them at once.

`src/routeTree.gen.ts` is generated by the TanStack Router Vite plugin from
files in `src/routes/` — never hand-edit it; it regenerates on `dev`/`build`.

## Architecture

### Module / stage data model

- `requisitions` is the central table. `module` (`M1`-`M7`) plus a free-form
  `module_data` JSONB column hold everything specific to that request type —
  there's no per-module table. Each `src/routes/<module>.tsx` file both
  renders the multi-step creation wizard **and** defines the exact shape it
  writes into `module_data` (grep the route file for `const moduleData = {`
  to find the authoritative field list — it's not documented elsewhere).
- Stages V2 (`quotations`/`quotation_suppliers`) → V3 (`approvals`) → V4
  (`purchases`) → V5 (`receipts`) are separate tables joined by
  `requisition_id`, each with its own route (`quoting.tsx`, `approval.tsx`,
  `purchasing.tsx`, `receipt.tsx`).
- `audit_logs` records every transition (action + actor + JSON details);
  `src/lib/audit-actions.ts` is the single source of truth for translating
  action codes to Portuguese labels — don't duplicate that map elsewhere
  (it used to be duplicated in the PDF template and drifted out of sync).
- M7 (Quadro de Comando) is architecturally separate: it has its own tables
  (`comando_pedidos`, `comando_anexos`, `comando_auditoria`), a public
  unauthenticated form at `/pedido-comando/$token` (token-gated, service-role
  server functions in `src/features/comando/api.ts`, no RLS-backed session),
  and an internal panel at `/comando`.

### Client vs. server data access

Two parallel patterns, don't mix them up:
- **Browser, session-scoped, RLS-enforced:** `supabaseBrowser` (from
  `src/lib/supabase-browser.ts`) used directly in route components and in
  each feature's `client.ts`. This is the default for anything an
  authenticated user does.
- **Server function, service-role, bypasses RLS:** `createServerFn` (from
  `@tanstack/react-start`) in each feature's `api.ts`, calling
  `supabaseRest()` (`src/lib/supabase-rest.ts`) with the service-role key
  from `src/lib/env.ts`. Used where there's no user session to scope RLS to
  (the M7 public token form) or where a controlled server-side operation is
  required. `getSupabaseEnv()`/`requireEnv()` in `env.ts` **throw** if
  `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`
  are missing — this exact failure mode took production down on 2026-08-18
  (see `docs/reports/2026-08-18-deploy-outage-esbuild-envvars.md`).

### PDF generation

Entirely client-side, no backend service: `src/features/pdf/client.ts`
fetches all data for a ticket, `src/features/pdf/template.ts::buildHtml()`
renders it to an HTML string, then `html2canvas-pro` + `jsPDF` rasterize it
in a hidden iframe and the result is uploaded to the `requisition-pdfs`
storage bucket. `buildHtml()` has a **dedicated, hand-written block per
module** for M1/M2/M5/M6 (M3/M4 fall through to a generic
`Object.entries(moduleData)` dump). **These dedicated blocks do not
auto-update when a route's `moduleData` shape changes** — when you add a
field to a module's `module_data`, check whether `template.ts` has a
dedicated branch for that module and update it by hand, or it'll silently
print `—` or omit the field entirely (this exact bug shipped for M2, see
`docs/reports/2026-08-18-pdf-m2-viagem-dados-completos.md`). M7 has its own
separate template (`src/features/comando/pdf-template.ts` +
`src/features/comando/pdf.ts`), reusing `renderHtmlToPdfBlob` from
`features/pdf/client.ts` but not `buildHtml()`.

### Deploy — two independent pipelines on every push to `main`

`.github/workflows/deploy.yml` SSHes in and builds
`~/domains/vprequisicoes.vpsistema.com/nodejs/` as a validation step, but
**the Hostinger "Node.js App" panel deploys independently** (its own
GitHub webhook) into `~/domains/.../hbuilds/versions/<uuid>/`, symlinking
`hbuilds/current` — and that's what Passenger actually serves. The two
compete for the same shared-hosting thread/process limits, which can crash
the native `esbuild`/Vite build (`GOMAXPROCS=2` in `scripts/build.mjs`
mitigates this; that script also backs up/restores `dist/` so a failed
build never leaves the site without a working artifact). Full writeup and
the required production environment variables:
`DEPLOY_HOSTINGER.md` and `docs/reports/2026-08-18-deploy-outage-esbuild-envvars.md`.

### Testing

Vitest + `jsdom` + Testing Library, config in `vitest.config.ts` (`@/` alias
mirrors the app's Vite alias). Tests live in `__tests__/` folders next to
the code they cover, not in a separate top-level test tree.

## Keeping this repo's docs useful

After finishing a task, add one line to `CHANGELOG.md` (most recent at the
top). For anything with real investigative content (root-cause analysis,
an incident, a non-obvious bug) worth preserving, write it to
`docs/reports/YYYY-MM-DD-slug.md` and link it from the `CHANGELOG.md`
entry — don't drop new standalone `.md` report files in the repo root.
